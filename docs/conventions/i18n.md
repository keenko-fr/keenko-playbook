# Localization

Use Paraglide/Inlang for product/interface copy and Sherlock as the preferred authoring/navigation workflow.

## Message storage

Use one canonical locale catalog per locale, for example:

```text
messages/fr.json
messages/en.json
```

Keep message IDs flat. The catalog may be large; source usage, generated function imports, and Sherlock provide locality.

Message IDs are stable identities, not descriptions of copy/hierarchy/location. Prefer Sherlock-generated random human-readable IDs. Keep an established ID when copy or component location changes but the underlying product message remains the same.

Identical current text does not imply shared identity. Use separate IDs when messages may evolve independently; share only when they intentionally represent one product message that should change together.

## Authoring

Preferred flow:

1. write/identify the intended UI copy;
2. use Sherlock extraction;
3. accept the generated stable human-readable ID;
4. call the generated message function directly, normally through an import such as `import * as m from "@/paraglide/messages"` according to the project's generated path.

Do not add a generic copy/useTranslations wrapper around generated Paraglide functions unless the framework genuinely requires one.

## Ownership

Paraglide owns product/interface copy, not editorial/database content. User-facing application copy should go through localization even in a single-locale product, except explicit prototypes/tests/nonlocalized technical surfaces.

Keep canonical domain/programmatic values in English and localize only at presentation boundaries.

Use the active locale for dates, numbers, currencies, and related output rather than hardcoding locale identifiers throughout components. Put plural/select grammar in message variants rather than assembling translated fragments in JSX.

Generated Paraglide output is compiler-owned, ignored by default, and deterministically compiled before typecheck/test/build. Never hand-edit generated modules.

Base locale, supported locales, routing/prefix/cookie/domain strategy, and adding a new locale are explicit project/product decisions rather than Keenko-wide French defaults.
