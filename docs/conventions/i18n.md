# Paraglide and application copy

## Message storage

Use one canonical flat message catalog per locale, for example:

```text
messages/fr.json
messages/en.json
```

Keep IDs flat even when the message-format plugin supports nested structures. Multiple feature-local catalogs are not the Keenko default.

## Message identities

Use stable random human-readable IDs generated by Sherlock. IDs are identities, not descriptions of wording, hierarchy, or component location.

- Do not rename an established ID merely because text changes or usage moves.
- Identical current text does not imply shared identity. Give messages separate IDs unless the usages intentionally represent the same product message and should evolve together.
- Sherlock extraction is the normal authoring workflow where available; direct catalog editing remains acceptable for translation/bulk work.

## Usage

Import generated Paraglide message functions directly. Do not add a Keenko `copy.ts`, `useTranslations()`, or other translation wrapper unless a framework integration genuinely requires one.

Paraglide owns intentional interface/product copy: labels, headings, validation messages, empty states, navigation, dialogs, toasts, and accessibility copy. Editorial/database content remains application data.

User-facing application copy goes through Paraglide even in a single-locale product, except explicit tests/prototypes/nonlocalized technical surfaces.

Stable programmatic values remain canonical English (`draft`, `published`, `failed`, etc.); localization happens in `DISPLAY` or validation-message mappings.

Use active-locale-aware formatting for dates, numbers, currencies, and related output rather than hardcoding locale identifiers throughout components. Put plural/select grammar in message variants rather than assembling translated fragments in JSX.

Generated Paraglide output is compiler-owned, ignored by default, and deterministically compiled before typecheck/test/build. Never hand-edit generated modules.

Base locale, supported locales, routing/prefix/cookie/domain strategy, and adding a new locale are explicit project/product decisions rather than Keenko-wide French defaults.
